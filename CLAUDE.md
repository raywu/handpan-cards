# CLAUDE.md - Handpan Chord Cards

Context for working on this repo. Everything below was established, measured,
or pixel-verified in the originating design session. Treat the "verified"
items as ground truth, not as conventions to second-guess.

## What this project is

A chord-card system for three specific handpans, in two output families that
share one data source:

1. **Web flashcard app** - `index.html`, single self-contained file, hosted on
   GitHub Pages. Vanilla JS + inline SVG, no build step, no dependencies
   except Google Fonts (system fallback offline).
2. **Print PDFs** - US Letter sheets of poker-size cards, styled after Sven
   Kirchhofer's "Handpan Training Cards" (the owner has the D Amara 9 set;
   measurements and conventions below were extracted from that PDF).
   Generated by `tools/hifi.py` + `tools/decks.py` (reportlab).

Decks: **C# Hijaz / Orion 9** (18 chords), **F3 Low Pygmy 18** (25 chords),
**D Amara 9** (16 chords, deduped from the commercial original).

## Repo layout

- `index.html` - the app. Deck data is embedded as `const DECKS = [...]`.
  For app work, this embedded JSON is the canonical data.
- `README.md` - usage, hosting, layout provenance notes.
- `*.pdf` - print outputs ("Cards" = full deck with title/legend/blank
  templates; "PRINTER_ONLY" = chord cards only, for the print shop).
- `tools/decks.py`, `tools/hifi.py` - print generator (see "Print pipeline").

## Hard constraints

- **Single-file app.** No bundlers, no frameworks, no external JS. Additions
  (PWA manifest/service worker are acceptable as sibling files) must keep
  `index.html` independently functional.
- **Do not alter deck data or diagram geometry** without explicit owner
  instruction. Layouts were verified against the physical instruments and
  some look "wrong" against generic handpan references - they are not.
- **Preserve the visual system** (fonts, palettes, card anatomy below).

## Instrument layouts (verified - do not "correct")

Angles are math-convention degrees (0 = right, 90 = up), y-up.

**C# Hijaz / Orion 9** - Ding C#3 centre. Standard left-first zig-zag:
1 G#3 @270, 2 B3 @225, 3 C#4 @315, 4 D4 @180, 5 F4 @0, 6 F#4 @135,
7 G#4 @45, 8 B4 @90. (F is functionally E#, the major third of C#.)

**F3 Low Pygmy 18** - Ding F3, enlarged and offset toward the player
(r=0.19R, dy=0.1425R below centre). Top rim is MIRRORED (right-first)
zig-zag: 1 G3 @290 (bottom-right), 2 Ab3 @250, 3 C4 @330, 4 Eb4 @210,
5 F4 @10, 6 G4 @170, 7 Ab4 @50, 8 C5 @130, 9 Eb5 @90 (top centre).
Inner pair beside the ding: 10 F5 @128 (left), 11 G5 @52 (right) - note
the inner pair ascends OPPOSITE to the rim direction; that is the real
instrument. Bottom notes drawn as an outer dashed ring in **x-ray view
(seen from above)**: U1 C3 @300, U2 Db3 @240, U3 Eb3 @0, U4 Bb3 @180,
U5 Db4 @60, U6 Ab5 @120. **Bb and Db exist only on the bottom shell** -
chords using them carry an orange "N BOTTOM NOTES" badge. Pitch-class set
is complete F natural minor.

**D Amara 9** - Ding D3. Standard zig-zag: 1 A3 @270, 2 C4 @225, 3 D4 @315,
4 E4 @180, 5 F4 @0, 6 G4 @135, 7 A4 @45, 8 C5 @90.

Session research finding: there is **no universal maker convention** for
bottom-note placement; layouts are per-instrument. Bottom shells are built
from below, so projected to top view their sequences typically run opposite
the top zig-zag (mirror geometry). Notation systems (e.g. Notepan) handle
this by attaching per-instrument images.

## Verified card conventions (pixel-validated against the original D Amara PDF)

1. **Pitch-class-complete highlighting.** The diagram lights EVERY field
   whose pitch class is in the chord, ding and bottom notes included.
   Root pitch class -> root colour on ALL its instances (double/triple
   roots are correct); other chord tones -> tone colour on all instances.
   Verified 16/16 original cards, including ding-as-green (Gsus4) and
   double-blue roots (C major: C4+C5).
2. **Bottom lines are in chord-spelling order from the root**, not pitch
   order (original: G5 = "6-3", Fmaj7 = "5-1-2-4"). Both the note line and
   the number line are coloured per note: root -> root colour, others ->
   tone colour, grey separators.
3. **Voicing rules** (audited from the originals): the ding never appears
   in a voicing; prefer the lowest compact root-position voicing; when a
   tone is only available below the root, cluster the voicing downward;
   power chords are two notes (root+5th); one card per pitch set (no sus2 -
   every sus2 duplicates a sus4; no 6-chords duplicating m7 sets); no
   doubled pitch classes in a voicing.
4. **Highlighted-field rendering:** thin black circle (always), coloured
   band inside at radius 0.87r with stroke 0.24r, inner black hairline at
   0.74r, label auto-fit inside. Unhighlighted bottom fields: dashed grey
   circle with grey label (receded).

## Design system

- **Type:** Oranienbaum (chord names, display), BioRhyme Expanded (note and
  number lines), Montserrat (labels/UI). All OFL; app loads from Google
  Fonts; print pipeline embeds TTFs.
- **Palettes** (root / tone; card frame is a horizontal gradient root->tone):
  - Hijaz: pink `#E0559A` / orange `#E2761B`
  - Pygmy: purple `#6D40A3` / gold `#C9971E` (gold deliberately darkened
    for text contrast on white)
  - Amara: original blue `#0097B2` / green `#00BF63`
  - Bottom-shell accents (Pygmy U-labels, badges): orange `#E27005`.
- **Card anatomy:** header (deck name, #index, blue scale-degree label,
  small-caps subtitle), Oranienbaum chord name with superscript, diagram,
  optional bottom-note badge, note line, number line.
- Scale degrees per deck: Hijaz {C#:I, D:bII, F#:iv, G#:v deg, B:bvii};
  Pygmy {F:i, Ab:III, Bb:iv, C:v, Db:VI, Eb:VII, G:ii deg};
  Amara {D:i, A:v, G:IV, C:bVII, F:bIII}.

## App data model (embedded DECKS JSON)

Per deck: `id, name, sub, colors{root,tone,ga,gb}, degrees{pc:label},
geom{...fractions of R}, fields{id:[name, octave, midi, zone, angle, label]},
chords[{main, sup, subtitle, fields[], roots[]}]`.
Zones: `ding | rim | inner | bottom`. `chords[].fields` is the canonical
voicing in spelling order; highlighting is DERIVED at render time from
pitch classes (midi % 12), never stored.

## Known pitfalls (hit during the session)

- **Boot order:** the first render must happen after the card-order array
  exists; `render()` guards against an empty order. Keep it that way.
- **Data re-injection:** the degrees contain `deg` (U+00B0) characters; a
  naive `re.sub(pattern, data)` treats them as escapes and silently fails.
  Use a lambda replacement, and ALWAYS verify by parsing the injected JSON
  back out of the written file - a smoke test against stale data passes.
- **Verification style:** invariant checks over all 59 cards (every voicing
  field lit; every root field root-coloured; no root/tone overlap) plus a
  DOM-stubbed boot simulation caught real bugs; keep both when refactoring.

## Print pipeline (tools/)

`python3 decks.py` builds all PDFs. Requirements: `pip install reportlab
pypdf`, and a `tools/fonts/` dir containing Oranienbaum-Regular,
BioRhymeExpanded-Regular/-Bold, Montserrat-Regular/-SemiBold TTFs (all on
Google Fonts / github.com/google/fonts, OFL).
Print spec, measured from the commercial original at 300dpi: card
**62.65 x 87.21 mm (177.6 x 247.2 pt, poker size)**, US Letter 3x3, gutters
12.2/9.4 pt, crop marks at all card edges, 2.00-inch calibration bar on
page 1 (instruct printers: 100% / Actual Size; verify the bar with a ruler).
If deck data changes: edit `decks.py`, rebuild PDFs, re-export the JSON and
re-inject into `index.html` so app and print never diverge.

## Hosting facts (checked against GitHub docs)

- Pages is free for public repos; private-repo Pages needs Pro/Team, and the
  published page is public regardless (Pages has no auth).
- Custom domains work on the free plan: CNAME record (subdomain) or
  A/ALIAS (apex) + the domain in repo Settings -> Pages. Routing is by Host
  header against GitHub's hostname->repo mapping, not DNS paths; with a
  custom domain the site serves at the domain ROOT (no /repo segment).
  Domain verification in account settings prevents takeover. HTTPS is
  automatic via Let's Encrypt.
