## Finding and boundary

**Partially verified feasibility:** the existing interface already supports a nonblocking duplicate warning, including enabled NEXT, GENERATE and SAVE CHANGES. Extending this to repeated exact pitches anywhere is feasible in the UI, but changing refusal copy or color alone is insufficient. The composer, parser, identity/serialization, and the active input path must all accept and preserve distinct physical positions before the UI can truthfully show successful updating. Core/engine lane findings and owner policy decisions remain dependencies.

No tests, browser runs, scripts, installation, remote writes or application edits were performed by this lane. The source walkthrough and proposed tests below do not establish passing regression or accessibility results. Pending owner answers must be reconciled before implementation. ## Proposed warning contract — provisional pending owner answers

1. **Meaning:** warn about two or more resolved identical MIDI pitches represented by separate physical fields. Different octaves sharing a pitch class are not duplicates for this warning. Enharmonic tokens that resolve to the same MIDI belong to one group. Resolve octave inference first; repeated typed letters alone do not prove repeated MIDI. Do not infer a physical copy from blog/import prose or a scale name.
2. **Preservation:** retain every entered occurrence as its own field through parse, preview, layout, save/edit, reload and supported share round trips. No silent deduplication, automatic octave change or confirmation gate. Existing genuine grammar, range, missing-required-input and unrelated layout refusals remain intact. Owner must settle which zones, including Ding-to-other-zone cases, qualify for admission.
3. **Fact versus presentation:** use one authoritative resolved multiplicity/group fact, with occurrence IDs and zones, rather than UI token matching. Keep transient warning presentation out of stable deck identity and share data unless protocol requirements independently require a version change. Engine lane owns protocol decisions.
4. **Copy:** prefer a factual, reassuring warning over a prohibition. Example: **“E4 appears twice in BOTTOM NOTES. Both positions are kept.”** For cross-zone copies: **“E4 appears in TOP RIM NOTES and BOTTOM NOTES. Both positions are kept.”** These are English drafts, not approved translation strings. Three copies require an accurate count and no “both.” Preserve original displayed spellings where practical; the implementation must not falsely call two enharmonic spellings different pitches.
5. **Minimal scope recommendation:** warn for newly admitted duplicate cases that previously refused, while preserving the existing inferred-bottom cross-zone warning. Do **not** automatically start warning for every already accepted explicitly written cross-zone unison: that would broaden warning policy and potentially add new notices to ordinary valid scales. Any broader content-based warning requires an owner decision. Compute duplication facts consistently across input paths, but preserve existing fields-path visibility and Scale-only presentation unless the owner explicitly selects broader visibility. A newly admitted valid combined line must still update, retain copies, and generate normally; warning visibility on this path needs a deliberate acceptance decision, since the current field warning clears on line focus. Do not duplicate independent notices or overwrite Layout feedback. Keep warnings hidden in Layout and restore them on Scale under the existing contract; persistent Layout visibility is a separate design change, not the default.
6. **Priority:** genuine errors/refusals remain primary and retain existing invalid markers. Duplicate warnings are secondary; inferred-octave/order information follows. Existing `syncMsgYield` suppresses general non-error/non-refusal messages when a field message is visible (`index.html:11090`), which can conceal crowded-label guidance. The plan must specify how every simultaneously relevant warning remains discoverable. Do not solve this by letting a duplicate warning suppress all other warnings indefinitely. Reuse a shared ordered message collection rather than create independent competing notice systems.
7. **Multiple groups:** provide a deterministic compact summary ordered by zone and occurrence, with accurate counts and complete accessible detail. Do not add a hard note cap or silently omit groups to fit the footer. If all details cannot fit existing tested budgets, the design review must select and test an existing compatible expandable/scrollable pattern before approval; this research does not authorize a new interaction architecture.

**Prefill consequence, verified source / inventory unverified:** opening Edit decomposes parsed fields into four explicit-octave strings (`index.html:12685`) and calls `paintFieldsOpen` (`12721`). The current inferred-bottom-only warning therefore does not normally warn for those explicit cross-zone copies. Broadening to all resolved cross-zone duplicates would introduce passive warnings on such Edit prefills, including built-ins/custom scales containing those unisons, despite no user edit. This lane has not inventoried which built-ins qualify and does not claim they all do. Before choosing broad coverage, enumerate affected canonical built-ins, supported share links and existing custom fixture records read-only, record exact affected counts, and show representative copy/fit cases to the owner. Merely opening an existing scale must not announce a new warning or alter its record.

## Accessibility grounding and limits

Dynamic feedback without a focus/context change needs a programmatically determinable status mechanism when it meets the status-message definition. WCAG guidance also cautions against unnecessary interruptions; a nonurgent permitted duplicate is a good candidate for the existing polite live region rather than an assertive alert. This is the proposed application choice, not a W3C requirement that every warning use one particular role. [W3C Understanding SC 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

Actual detected input errors must be identified and described in text; color alone does not suffice. Permitted duplicates should not be called validation errors solely because they repeat. Keep textual identification of genuine failures. [W3C Understanding SC 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html). The informative ARIA21 technique associates `aria-invalid` with failed validation; duplicate-only valid fields should keep it false or absent. [W3C ARIA21](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA21).

Avoid focus movement, rapidly vanishing warnings and frequent interruption; these recommendations also align with the informative APG alert guidance. A duplicate warning does not justify an interrupting alert dialog. [W3C APG Alert Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/). Automated DOM checks can verify associations, live-region updates and focus invariants; they cannot prove real VoiceOver/TalkBack delivery. Physical AT checks remain explicitly unverified until performed.
