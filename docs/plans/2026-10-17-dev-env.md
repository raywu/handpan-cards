# Plan: a DEV environment on one `dev` branch (2026-10-17)

This is a plan only. It writes no production code, creates no account, deploys nothing and changes no repo setting.
It is based on `origin/main` at eebd682.

Evidence marks:
- **[V]** verified against a primary source (URL given, read 2026-10-17) or the repo at eebd682 (file:line given).
- **[O]** observed by running something here on 2026-10-17.
- **[U]** UNVERIFIED: no primary source was found. It is never stated as fact.

Line numbers are for eebd682 and will drift. Lane briefs below cite anchors (a function, a test title or a YAML key), not lines.

## 1. Goal, non-goals, owner gates

**Goal (testable).** The owner opens `https://<project>.pages.dev/` on a phone with no login and sees the newest commit of the `dev` branch within minutes of it landing. That page loads no Google Analytics, answers with `X-Robots-Tag: noindex` and shows IMPORT TEXT. Meanwhile `index.html` on `main` is byte-identical to eebd682, and so is everything else GitHub Pages serves apart from one new file under `tools/`.

**Non-goals**
- No change to the GitHub Pages deploy: same source (`main`, `/`), same `CNAME`, same files apart from the new tool.
- No custom domain for DEV.
- No import feature work. DEV only un-hides what `main` already ships hidden.
- No build step on any branch. The vendor's build command is blank or `exit 0`.
- No change to `index.html`, `robots.txt`, `sitemap.xml`, `CNAME` or `.nojekyll` on `main`.
- No per-PR preview deployments, and no deploy of any branch except `dev`.
- No login, password or access policy on DEV (D1).

**Standing owner gates**
- Every OWNER-ONLY step in section 5 (account, GitHub App, dashboard settings, creating `dev`). The fleet never does these.
- Merging to `main` stays operator-gated, as today.
- Merging into `dev` needs a new AFK grant (Q1, section 8). Until the owner adds it, the owner merges dev PRs by hand.
- Any force-push, reset or delete of `dev` is an owner action. It is the escape hatch in section 6.6.

## 2. Research, matrix, recommendation

### 2.1 Vendor findings (all read 2026-10-17)

**Cloudflare Pages (free)**
- Pages is not deprecated. Only Workers *Sites* is. [V] https://developers.cloudflare.com/workers/wrangler/deprecations/ and https://developers.cloudflare.com/workers/static-assets/migrate-from-pages/
- **No build.** "When you are working without a framework, leave the Build command field blank." "If you are not using a preset, use exit 0 as your Build command." [V] https://developers.cloudflare.com/pages/configuration/build-configuration/
  - The value that serves the repo root as the output directory (blank or `/`) is not stated. [U] Section 5, step O3, checks it by opening the URL.
- **One branch only.**
  - Production branch controls offer an "Enable automatic production branch deployments" checkbox. [V] https://developers.cloudflare.com/pages/configuration/branch-build-controls/
  - Preview branches can be "None: Turns off automatic builds for all preview branches." "If a branch does not match either then it will be skipped." [V] same page
  - The production branch can be any branch. [V] same page
- **Stable URL.** A production deployment is served at `<project>.pages.dev`. A preview branch has the alias `<branch>.<project>.pages.dev`. [V] https://developers.cloudflare.com/pages/configuration/preview-deployments/
- **Public.** "By default, these deployment URLs are public." Cloudflare Access is opt-in. [V] same page
- **Noindex.**
  - Previews get `X-Robots-Tag: noindex` automatically. [V] same page
  - A production deployment does not get it, so this plan adds it through `_headers`.
  - "This file will not itself be served as a static asset," and it sits in the build output directory. [V] https://developers.cloudflare.com/pages/configuration/headers/
- **Limits.** 500 builds a month, 1 concurrent build, 20,000 files, 25 MiB per file. [V] https://developers.cloudflare.com/pages/platform/limits/
  - Static request quota: [U].
- **GitHub App.** Can be installed on "Only select repositories". [V] https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/
- **Checks on PRs.** Builds post check runs. Check runs "don't appear when a build is skipped" by branch controls or watch paths. [V] same page
  - Whether PR comments appear when previews are off: [U].
- **Doc-only skip.** Build watch paths take include and exclude globs, excludes first. A push with 3000+ changed files or 20+ commits always builds. [V] https://developers.cloudflare.com/pages/configuration/build-watch-paths/
  - Whether `docs/plans/*` also matches nested paths: [U].
- **Blast radius.** Cloudflare cannot touch `handpan.raywu.org` unless someone adds that domain to the project. The domain's DNS is on the owner's side. It never writes to the repo or to GitHub Pages. [V] by the App's permissions (checks and deployments), plus [A] for the DNS point.

**Vercel (Hobby)**
- Hobby is for personal, non-commercial use only. Commercial means financial gain, payments or "inclusion of advertisements". GA alone is not listed as commercial. [V] https://vercel.com/docs/limits/fair-use-guidelines
- 100 deployments a day. [V] https://vercel.com/docs/plans/hobby
- **Branch URL.** `<project>-git-<branch>-<scope>.vercel.app`, which "won't change if you push new commits". [V] https://vercel.com/docs/deployments/generated-urls
- **Ignoring other branches.** Either:
  - `git.deploymentEnabled` in `vercel.json`, where any branch not listed defaults to on [V] https://vercel.com/docs/project-configuration/git-configuration; or

- **Noise and quota.** Cancelled builds still count against the quota, and every pushed branch still gets a "skipped" commit status [V] https://vercel.com/docs/git/vercel-for-github. With the swarm's `claude/*` churn, that is noise on every lane.

- **Permissions.** The GitHub App asks for Administration, Checks and Commit statuses, all read and write. [V] vercel-for-github page

**Netlify (free)**
- **Credits.** 300 credits a month, as a hard limit. A production deploy costs 15 credits. Branch deploys are not metered. [V] https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/
  - If `dev` is the production branch, that allows about 20 deploys a month.

**GitHub Pages, second repo**

## 3. Design

### 3.1 Branch model (D2)

**One flow per lane PR.** The fewest steps that keep `main`'s gate intact.

1. The lane pushes `claude/<lane>` and opens PR **M** with base `main`, as today. CI runs on M and is the evidence (section 3.5).
2. The integrator opens PR **D** with the same head and base `dev`: `gh pr create --base dev --head claude/<lane> --title "DEV: <lane>" --body "Evaluate on DEV; main PR #<M>"`. GitHub allows two open PRs from one head to different bases. [A]
3. **Dev gate (lighter than main's).**
   - CI on PR M is green at the head SHA that D carries. Check `gh pr view <D> --json headRefOid` against `gh run list --commit <sha> --workflow validate`.
   - D must not be CONFLICTING.
   - No reviewer is needed.
   - Then `gh pr merge <D> --merge`.
4. Cloudflare builds `dev`. The integrator posts the DEV URL and the `dev` SHA on PR M (section 7).
5. The owner evaluates on the phone.
6. PR M then goes through the unchanged main gate: CI green at the verified head SHA, a fresh reviewer PASS, operator merge.

The lane never PRs `dev` into `main`. `dev` carries the overlay (3.3) and lanes not yet accepted, so `main` never receives it.

**Doc-only PRs** (section 3.5's definition) skip steps 2 to 5. Nothing about them can be evaluated in a browser (Q3).

**Keeping `dev` in step with `main` (no force-push).** After every merge to `main`, the integrator does the following:
- opens a sync PR, `gh pr create --base dev --head main --title "Sync main into dev"`;
- merges it with `gh pr merge <n> --merge`.

`dev` only ever moves by merge commits through PRs.

If a sync PR is CONFLICTING, the integrator:
- branches `claude/dev-sync-<date>` from `origin/dev`;
- runs `git merge origin/main` and resolves the conflict, taking `main`'s side everywhere except the overlay lines in 3.3;
- re-runs `python3 tools/inline_engine.py` and `python3 tools/sync_decks.py` if a generated region conflicted, as CLAUDE.md "Hard constraints" requires (CLAUDE.md:83-96);
- PRs that branch into `dev`.

`main` is never touched.

**Rejection on DEV.**
- The integrator branches `claude/dev-revert-<lane>` from `origin/dev`, runs `git revert -m 1 <D's merge commit>`, PRs it to `dev` and merges it. That is a new commit, not a rewrite.
- PR M is closed, or reworked.
- **Reworked work goes on a fresh branch from `origin/main`** (new SHAs, for example cherry-picked). Re-merging the old branch into `dev` would not bring back the reverted commits; that is the revert-a-merge trap.
- The fresh branch merges cleanly into `dev`. The merge base is a `main` commit, and on `dev` the reverted lines are net unchanged.

**Escape hatch (OWNER-ONLY).** If `dev` drifts beyond repair, the owner recreates it from `main` (section 5, O6), and the overlay PR is re-opened from `claude/dev-overlay`.

### 3.3 The dev overlay (dev-only; never on `main`)

One PR from `claude/dev-overlay` into `dev`. That branch is never PR'd to `main` and never deleted. It changes exactly these bytes.

1. **`index.html`, the `GA_MEASUREMENT_ID` constant** (index.html:12265).
   - Before: `const GA_MEASUREMENT_ID = "G-QTYWB2HSSV";`
   - After: `const GA_MEASUREMENT_ID = "G-XXXXXXXXXX";`
   - `analyticsAllowed()` returns false for the placeholder (index.html:12269-12274, `return GA_MEASUREMENT_ID !== "G-XXXXXXXXXX";`).
   - `loadAnalytics()` is the only code path that adds a network request to Google (index.html:12276-12283). The head script only fills `window.dataLayer` (index.html:53-63).
   - The same placeholder is already proven to disable everything by the test "analyticsAllowed is false for the placeholder id: no gtag script, no config, no event" (tests/app.test.js, the `noInject` table after "the loader appends the gtag script on a real host with a real id, and only then").
2. **`index.html`, the `#import-row` tag** (index.html:1384).
   - Before: `<div class="fieldrow" id="import-row" hidden>`
   - After: `<div class="fieldrow" id="import-row">`
   - This is exactly the change the mutants `ib_import_row_not_hidden.patch` and `ib_import_row_not_hidden_e2e.patch` make, so `main`'s tests are known to catch it there.
3. **New file `_headers`** (repo root on `dev` only):

   ```
   /*
     X-Robots-Tag: noindex
   ```

   Cloudflare reads the file and never serves it. [V] headers page. It never exists on `main`, so GitHub Pages never serves it either.

Nothing else changes.
- The canonical link (index.html:23) still names production, which also tells crawlers which page counts.
- `robots.txt` stays `Allow: /`. A crawler has to fetch the page to see its noindex, and a `Disallow` would hide it. [A]

**Why the overlay instead of production code (D4, and the GA question).**
- A host check inside `analyticsAllowed()` would change production bytes.
- It would also break "the shipped index.html boots unmodified on a real host and loads gtag with the shipped id". That test boots on `https://example.test/` (tests/app.test.js:9441-9447) and needs `analyticsAllowed()` true there.
- So it would need new tests, new mutants and an allowlist of production hosts.
- The overlay is two lines that only `dev` carries, and `main`'s own tests already pin both lines on `main` (section 4).

**The cost of the overlay.**
- A main→dev sync conflicts only when `main` edits one of those two lines. A future import lane that un-hides for real is the one foreseeable case: resolve it by taking `main`.
- DEV runs no CI (3.5), because the overlay would redden every test that pins these lines.

### 3.4 Storage and share links

- localStorage is per origin, so DEV (`<project>.pages.dev`) can neither read nor write production users' `hpfc` store (index.html:8500 `const STORE_KEY = "hpfc"`). Decks made on production are not on DEV.
- To move a deck across, COPY LINK on one origin and swap the host: `https://<project>.pages.dev/#s=5/...`. The `#s=` code is origin-free.
- A DEV build that writes a newer wire version than production gets `NEEDS_NEWER_APP` on production, by design (CLAUDE.md "Share link v5", "SV: a 5 not followed by / is BAD_NOTE, and 6 or above is NEEDS_NEWER_APP").
- Links shared from DEV point at DEV. Never post them where users will find them.

### 3.5 CI changes (one lane, on `main`)

`.github/workflows/validate.yml` changes in two ways.

**(a) CI runs only on PRs into `main`.**
- `on.pull_request` (validate.yml:6) becomes:

  ```yaml
    pull_request:
      branches: [main]
  ```

- Without this, every D PR runs CI against `dev`. That run goes red on the overlay ("the shipped measurement id is G-QTYWB2HSSV", "IM: the import row ships hidden...", and mutants that no longer apply).
- Worse, `gh run list --commit <lane head>` would then show two runs for one SHA, one green and one red. That breaks the integrator's gate.
- Sync PRs (head `main`) need no run, because `main` was already CI'd.
- `panel-fit` already compares against `origin/main` on `pull_request` (validate.yml:217), which stays right.

**(b) Doc-only PRs skip every job but still report success (D3).**
- No branch protection exists today: `gh api repos/raywu/handpan-cards/branches/main/protection` returned 404 "Branch not protected", and the rulesets list is `[]`. [O]
- `paths-ignore` would still be wrong. A skipped workflow leaves no run for `gh run list` and a "Pending" check if protection is ever added. [V] GitHub doc above
- So this plan uses a `changes` job and job-level `if:`. A skipped job reports success. [V]

New first job:

```yaml
  changes:
    name: changes
    runs-on: ubuntu-latest
    outputs:
      code: ${{ steps.scope.outputs.code }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 2
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      # A push that is not a merge commit always runs everything (fail closed).
      - id: scope
        shell: bash
        run: |
          if [ "${{ github.event_name }}" = "push" ] && ! git rev-parse -q --verify HEAD^2 >/dev/null; then
            echo "code=true"
          else
            git diff --no-renames --name-only HEAD^1 HEAD | python3 tools/ci_scope.py
          fi >> "$GITHUB_OUTPUT"
```

Every other job changes as follows:
- `data`, `python-tests`, `js-tests`, `mutation-gate-shard` and `panel-fit` gain `needs: changes` and `if: needs.changes.outputs.code == 'true'`.
- `suite-health` becomes `needs: [changes, python-tests, js-tests]` and `if: always() && needs.changes.outputs.code != 'false'`.
- `mutation-gate` becomes `needs: [changes, mutation-gate-shard]` and `if: always() && needs.changes.outputs.code != 'false'`.

Fail-closed cases:
- If `changes` fails, the plain jobs are skipped but the run is red, because `changes` failed. The two `always()` jobs run with an empty output and fail on missing artifacts.
- `--no-renames` makes a move of `README.md` into `docs/plans/` show as a deletion of `README.md`, so it runs CI.
- A pull_request checkout is the merge ref, so `HEAD^1` is the base tip. A push to `main` is a PR merge commit (`gh pr merge --merge`), so `HEAD^1` is the old tip.

New file `tools/ci_scope.py`:

```python
import sys

DOC_ONLY = ("docs/plans/", "docs/prompts/")


def code_changed(paths):
    paths = [p.strip() for p in paths if p.strip()]
    return not paths or any(not p.startswith(DOC_ONLY) for p in paths)


if __name__ == "__main__":
    print("code=" + ("true" if code_changed(sys.stdin) else "false"))
```

**What counts as doc-only, and the proof.** I grepped every test and tool for a doc it reads:

```
grep -rnE "README|CLAUDE\.md|docs/|TODOS|\.md[\"']" tests tools --include='*.py' --include='*.js' --include='*.sh'
```

The files that are read [O]:
- `README.md`, by tests/test_readme_currency.py:19.
- `CLAUDE.md`, by the line-ref ratchet `LINE_REF_FILES` in tests/test_readme_currency.py:195.
- `docs/ENGINE-SPEC.md`, by tests/core.test.js:22, tests/share.test.js:30, tests/select.test.js:37 and tests/app.test.js:1217.
- `README.md` is also patched by the mutant `m_readme_card_count_stale.patch`.

No test or tool reads anything under `docs/plans/` or `docs/prompts/`. The only hits are comments naming a plan, for example tests/test_readme_currency.py:9.

So only those two trees are doc-only.
- `TODOS.md`, `docs/SCALE_ENGINE_PLAN.md` and `docs/ui/` are not read today either. They are left out to keep the rule obvious, and they still run CI.
- `CLAUDE.md`, `README.md` and `docs/ENGINE-SPEC.md` always run CI.

**The vendor's doc-only skip.**
- Cloudflare build watch paths (O4): include `*`, exclude `docs/plans/*` and `docs/prompts/*`.
- In practice doc-only PRs never reach `dev` (3.1), so this only trims sync merges. At 500 builds a month it is optional.

**Vendor checks and the gate.**
- Cloudflare builds only `dev`. Its check runs land on `dev` merge commits, never on a lane head SHA or a PR into `main`. [V] skipped builds post no check run
- So `gh pr checks <M>` and `gh run list --commit <head>` never show Cloudflare.
- Gate rule (CLAUDE.md, lane C): the merge gate reads only the `validate` workflow's run conclusion. A vendor check is never made required. If one ever shows on a main PR, it is informational, and its colour neither blocks nor passes a merge.

## 8. Risks and open questions

**Risks**

| Risk | Mitigation |
|---|---|
| A cleanup step deletes a lane branch because its D PR shows "merged" while PR M is still open | Cleanup checks `--base main` (CLAUDE.md DEV section, lane C; Q2 changes the global rule). |

| A future branch-protection rule requires a vendor check | Never require it. T5 keeps Actions the only gate. |
| Overlay conflicts on sync | Only the two overlay lines can conflict; resolve to `main` except those lines (3.1). |
| GA still receives DEV hits | Not possible while the placeholder id holds (the `noInject` test). O3 checks it live. |
