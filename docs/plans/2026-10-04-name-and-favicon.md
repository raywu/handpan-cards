# Plan: site name, metadata and favicon

Status: ENG-REVIEWED 2026-10-04 (§8, ledger D1-D4 plus four outside-voice
findings adopted); awaiting `/plan-design-review` (§9).
Owner decisions (interview 2026-10-04): visible name **Handpan Chords**;
favicon **pan with a lit triad**; scope **title + description + Open Graph +
favicon set** (no web manifest).

## 1. Goal

The site at https://handpan.raywu.org/ shows ONE name everywhere a person can
read it, carries a description that says what it is for (chords AND chord
progressions, by scale), and has a favicon that reads as a handpan with a chord
lit on it. Today the tab says "Handpan Chord Flashcards", the page says
"Handpan Chord Cards", the README says a third thing, there is no favicon, and
a shared link previews as a bare URL.

Done when, on main:

1. `<title>`, `<h1>`, `og:title` and the README H1 all read `Handpan Chords`.
2. `<meta name="description">` and `og:description` carry the progression
   value-add (copy in §3.2) and are 120 to 160 characters.
3. `<link rel="icon">` is an inline SVG data URI (§3.3), and
   `apple-touch-icon.png` (180x180) and `og.png` (1200x630) exist at the repo
   root, generated by `tools/make_icons.py` from that same SVG.
4. `python3 tools/make_icons.py --check` reports the PNGs current (within the
   §3.4 tolerance), the way `inline_engine.py --check` does for the engine: a
   SYNC step, not a build step.
5. The new tests in §4 pass locally and in CI at the merged SHA; every
   existing oracle (validate, inline_engine, sync_decks, refresh_mutants,
   suite_health, mutation gate) stays green.

## 2. Non-goals

- No change to deck data, diagram geometry, card anatomy, fonts or palettes.
- No web manifest, service worker or PWA work (owner, 2026-09-30 and today).
- The PRINT outputs keep their titles: `decks.json` `print.title` strings
  ("... - Chord Cards"), `hifi.py`'s docstring, and `pdfcards.js`'s PDF
  document title (`name + " - Chord Cards"`) are the print product's naming
  and are untouched. `CLAUDE.md` line 1 is an internal heading; untouched.
- No new domain. The site stays at handpan.raywu.org; `CNAME` is untouched.
- No header tagline. The h1 stays a single short phrase: the 320x568 overlap
  test (`tests/e2e.test.js`, "the header title and the settings trigger do
  not overlap at 320x568") is the reason.
- No favicon.ico. Chromium and Firefox take the SVG; Safari (desktop and
  iOS) takes `apple-touch-icon.png`.
- No version pin on PyMuPDF (D3 chose a tolerance oracle instead).

## 3. Design

### 3.1 Name

Visible name: **Handpan Chords**. Research 2026-10-04: no live product uses
it. handpanchords.com is registered but serves an empty placeholder; a
zero-star GitHub repo `panchords` exists. The nearest established products

`theme-color` and `color-scheme` stay where they are; the existing

### 3.3 Favicon: Amara's Dm card, seen from above

One SVG, `viewBox="0 0 64 64"`, no text, no gradients, no filters:

| element | geometry | fill / stroke |
|---|---|---|
| ground disc | circle c=(32,32) r=32 | fill `#1a1815` (the `--table` token) |
| rim | circle r=27 | stroke `#f4f0e8` (the h1 colour), width 3, no fill |
| ding | circle c=(32,32) r=6.5 | stroke `#f4f0e8` width 2.5, no fill |
| 5 unlit fields | circles r=4.5 on radius 18.5 at the Amara angles 270, 225, 180, 135, 90 (math degrees, y-up) | stroke `#f4f0e8` width 2.5, no fill |
| lit root | circle r=6 on radius 18.5 at 315 (D4) | fill `#0B7B75` (Amara root teal), no stroke |
| lit tones | circles r=6 on radius 18.5 at 0 (F4) and 45 (A4) | fill `#DD8F00` (Amara tone amber), no stroke |

Still 11 circles, so §4 test 3 is unchanged. The strokes are the design
review's change (§9, finding F1): the first draft (rim 1.5, fields 1.2 on
r=5) rasterised at 16 px to 0.3-0.4 px hairlines that anti-aliased into grey
noise around two amber spots, and the ground disc vanished on a dark tab
strip. With rim 3 / strokes 2.5 and lit fields r=6 against unlit r=4.5, the
16 px raster reads as a pale ring, a pale ding and three filled dots (one
teal, two amber) on BOTH Chrome's dark strip (`#202124`) and a light one
(`#dee1e6`); verified on real PyMuPDF rasters at 16 and 32 px,
`strip-dark-v2.png` and `strip-light-v2.png` in the Approved Mockups below.

That is the D minor card of the D Amara deck, the first card of the first
built-in deck the app shows, drawn with the app's own highlighting rule (root
colour on the root, tone colour on the others). It is the product's own
diagram, not a generic icon. ONE SVG, no `sizes="16x16"` second icon (§9,
decision N13): Chromium ignores `sizes` on SVG icons and takes the last one,
so a second inline SVG is a second source to keep in sync for one browser
family's benefit, and the thicker-stroke single SVG already reads at 16 px.

The data URI is the URL-encoded SVG (`#` -> `%23`, `"` -> `'`, spaces kept),
so it stays diff-readable in `index.html`; no base64.

### 3.4 `tools/make_icons.py` (new) and the two PNGs

- Reads `index.html`, extracts the `rel="icon"` data URI, decodes it to SVG
  text. `index.html` is the ONLY copy of the icon; there is no `icon.svg`.
- Renders `apple-touch-icon.png` 180x180 from that SVG with **PyMuPDF**
  (already in `requirements-ci.txt`; `fitz.open(stream=svg, filetype="svg")`
  then `get_pixmap(matrix=...)`; probed 2026-10-04 on PyMuPDF 1.26.5, the
  SVG opens as a 64x64 page and renders 180x180 with alpha). iOS squares the
  corners itself, so the full ground disc is drawn on a `#1a1815` square.
- Renders `og.png` 1200x630, ONE centred stack inside the square-crop safe
  zone x 285..915 (§9, finding F2: WhatsApp, iMessage, LinkedIn mobile and
  Slack crop 1200x630 to the centre 630x630; the first draft's left icon and
  96 px title were cut on both sides, and the title alone was 728 px wide from
  x=480, past the 1200 px edge). `#1a1815` ground, everything `#f4f0e8` except
  the lit fields, every line horizontally centred on x=600:
  - icon 240 px, rect (480, 84) to (720, 324);
  - "Handpan Chords", Marcellus 72 px, baseline y=432 (546 px wide);
  - "Learn chords. Play progressions.", Nunito Sans 36 px, baseline y=490
    (522 px wide);
  - "For your handpan scale.", Nunito Sans 36 px, baseline y=538 (385 px).
  Widest line 546 px, so the whole stack sits inside 630 with 42 px to spare
  on each side of the square crop. Fonts from `tools/fonts/` (already checked
  in with their OFL texts); text drawn by PyMuPDF `insert_text` with
  `fontfile=`, centred from `fitz.Font(fontfile=...).text_length()`.
  Rendered reference: `og-v2.png` and its square crop `og-v2-square.png`
  in the Approved Mockups below.
- `--check` re-renders both into memory and compares them with the files on
  disk under a TOLERANCE, not byte equality (D3): `requirements-ci.txt` does
  NOT pin PyMuPDF, so anti-aliasing may differ by a version between the
  machine that committed the PNGs and the CI runner. A PNG is CURRENT when
  the two images have the same size and at most 0.5% of pixels differ by more
  than 24/255 in any channel. A changed SVG colour or a moved field changes
  whole discs (a 5/64 field at 180 px is ~600 px, 1.9% of the icon) and fails
  the check by an order of magnitude. Non-zero exit and a one-line report per
  stale file. The §4 test calls the same function.
- `render()` returns the two images; `check()` returns the per-file verdict
  with the measured differing fraction, so a failure message says HOW stale.
- No new dependency. No ImageMagick, no cairosvg, no version pin.
