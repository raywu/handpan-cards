## Required deep research

### A. Demand and differentiation

Investigate family/key/note-count/maker/layout/search-language synonyms and learning
intents. Separate a real popular layout from an owner's illustrative name or
an unverified “popular” claim. Do not invent volumes, rankings or conversion rates.
Search results are dated/location-dependent observations, not Search Console data.
Use primary maker catalogs for note sets where possible; record conflicting layouts,
unavailable evidence and permission/attribution needs. Do not copy marketing prose.

Test the hypothesis against alternatives: a handful of substantial scale lessons,
one consolidated scale-family guide with variants, an interactive reference or
remaining app-only. Define what each page uniquely teaches beyond swapped names/
transpositions. Cover real progression examples, why they work, limitations,
practice/rhythm suggestions and novice/intermediate suitability only where evidence
supports them. Avoid false first-hand playing claims or fabricated sound samples.

### B. Search quality and architecture

Browse current authoritative primary sources: Google people-first/AI/scaled-content
policies, doorway/duplicate/canonical behavior, crawlable links and URL fragments,
structured data, sitemaps and measurement. Cite direct URLs near claims with dates;
short quotes only. Separate documented requirements, inferred risks and hypotheses.
Do not turn one policy into a ranking guarantee or present AI as automatically banned.

Evaluate crawlable article URLs versus existing fragment-driven custom app states;
the exact-scale CTA is a user destination, not evidence that every hash is an
independently indexable page. Preserve the single-file app/no-build guarantee and
current root-only sitemap tests unless a concrete owner-approved architecture
change is proposed. Compare minimal static sibling content, separate content
hosting/repo and external publishing without installing or setting up any option.
Specify canonical/redirect/noindex/internal-link/sitemap/metadata behavior, migration
costs, accessibility/performance and ownership. No automatic programmatic page explosion.

### C. Engine truth and exact-link integrity

Inspect the actual API and rank/difficulty/sequence semantics; do not invent a
progression API or equate engine labels with verified musical teaching expertise.
Use only validated non-mutating diagnostics in isolated artifacts if appropriate.
Decode the supplied v6 link through the canonical reader, validate checksum/options,
enumerate zones/octaves/note counts and compare its actual layout with the query
example. Do not silently retitle an18-note variant as a20-note instrument.
If web access fails, record tool unavailability and rely on source-backed decoding;
do not call the site broken. Never import into the owner's browser/profile/storage.

Establish a source-backed article→app arrival matrix. Separate supported instrument/
layout restoration from progression/tier/style/view restoration for fresh users,
returning users, repeated arrivals and blocked/unavailable storage. The current
share contract carries the instrument and options, never the generated deck;
stored mode/tier and random sequence selection can change arrival behavior. Do
not promise that a link opens the published progression without evidence. Define
truthful CTA wording and existing-UI instructions as the no-app-change fallback;
any richer deep-link capability requires separately approved app implementation.

Distinguish the musical instrument seed from an RNG seed. Editorial records must
pin engine revision, canonical instrument/options, locale, difficulty, RNG procedure/
seed, prior-sequence input where relevant and resolved chord identities/voicings/
style. Pinning the instrument alone does not reproduce a progression. Verify event
coverage for repeated arrivals: current share_open suppression for an already-
restored deck means it cannot automatically measure every article-to-app arrival.
Do not equate an event count with exact progression delivery.

Require reproducible pinned engine/seed/options/locale results, available chord
tones, relevant voicings and a named musical/editorial review gate. “Nice” and
beginner/intermediate appropriateness need honest human validation or qualified
heuristic language. Include unsupported/unsolvable/low-progression scales and
aliases; don't fabricate rich lessons for unsuitable inventories.

Propose exact-link round-trip tests, backward-reader maintenance, name/count/seed
alignment, layout-option/angle validity, escaping/checksum/copy tests and query-
before-hash attribution order. Stored records/share compatibility and English
note-input conventions remain unchanged. Do not add raw scales/names/hash payloads
to analytics or propose an unbounded combination of indexable custom states.

### D. Tactical editorial and operating system

Define an explicit proposed pipeline: discover demand → verify instrument/layout
provenance → generate/pin candidate chords/progressions → musical review → useful
article draft/diagrams → editorial/source/fact QA → technical link/SEO/accessibility
checks → approved publication → monitoring → versioned corrections/retirement.

Specify artifact/schema fields, owners/skills/tools, human capacity/time per page,
deduplication/cannibalization controls, citations/credits/transparency, templates
with required unique sections, change detection and maintenance/rollback. Distinguish
deterministic engine output from generated explanation; don't let a language model
invent notes, chords, testimonials, maker layouts, dates or review outcomes.
Keep one source of truth without sharing production logic as its test oracle.

### E. Pilot and measurement

Propose a bounded pilot with entry/stop/expand conditions, target query clusters,
eligible article count, editorial cost and a sensible observation window grounded
in actual indexing/data availability. Mark numeric assumptions; no traffic promises.
Investigate aggregate Search Console query/page impressions/clicks/index coverage
and existing GA4 funnel events. Domain ownership was already owner-verified;
current Codex auth/export access is unverified—don't ask to repeat verification or
copy credentials. Ask for minimal relevant aggregate exports if required.

Separate content impression/click, article usefulness, CTA click, successful exact-
scale arrival and meaningful practice engagement. Audit existing nine events and
privacy filters before proposing new event names. Attribute without full private
share hashes/names, internal UTM session resets or polluted test/DEV traffic.
Distinguish missing instrumentation, sparse data, no indexing and a rejected
strategy; define safe corrective decisions rather than endless automatic output.
