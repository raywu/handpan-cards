# Prompt: plan the Handpan Theory rebrand and the move to handpantheory.com

Paste everything below the line into a fresh Claude Code session on
`raywu/handpan-cards`. It asks for a PLAN and cheap visual explorations, not a
shipped change.

---

You are planning, not shipping. The owner wants to rebrand the app as
**Handpan Theory** (lockup tagline **CHORDS & PROGRESSIONS**) and move it from
`handpan.raywu.org` to `handpantheory.com`. Your job is to explore several
directions quickly, show them, and write a plan the owner can steer. Keep
every option open until the owner picks; nothing you do in this session
should be hard to undo.

## Owner decisions (2026-10-31)

1. **Name: Handpan Theory.** Users must still understand that the app at the
   site root is for chords AND chord progressions, so that concept is the
   subtitle. Default: lockup tagline `CHORDS & PROGRESSIONS`; in running text
   (title, description, a line under the header) "chords and chord
   progressions" in full. How the subtitle shows in the app header, `<title>`,
   `h1`, `og:title` and the JSON-LD WebSite node is open for exploration, as
   long as the concept is visible at the root and the SEO structure holds.
2. **Logo: redrawn to SVG from measurements of the board** (no owner vector
   exists). The set is in `docs/brand/logo/` (marks, lockups, app icons),
   generated by `docs/brand/make_logo.py` from one measured geometry
   (`docs/plans/2026-10-31-logo-redraw.md`), wordmark outlined from
   `tools/fonts`. The mark matches the board; `mark-small` is for 24-48px. A
   direction may propose changes, made in the generator and re-checked with
   `docs/brand/redraw/check_mark.py`, never by hand-editing an SVG.
3. **Canonical host: `handpantheory.com` (apex).** `www.handpantheory.com`
   301s to the apex.
4. **Cloudflare runs the new domain** (DNS, and the natural place for the
   www and old-host redirects and for hosting via the Cloudflare Pages prod
   project that raywu/handpan-cards#727 prepared). Verify whether
   `handpan.raywu.org` is also on Cloudflare (the repository-rename plan says
   it is a proxied CNAME) and whether serving stays on GitHub Pages or moves
   to Cloudflare Pages; recommend one with reasons.

## Fixed (not up for exploration)

1. **No functional change.** Same features, routes (`#deck=`, `#s=`), storage
   keys, analytics events, gestures, i18n behaviour. If a direction needs a
   functional change, list it as a separate, optional follow-up.
2. **No SEO design change.** Keep the structure: one canonical per page,
   `og:*` set, JSON-LD WebSite node, sitemap, `llms.txt`, robots, per-scale
   pages, `handpan-101`, noindex scoping, the analytics privacy rules. Only
   VALUES change (host, and the brand name if the owner says so). The plan
   must say how the old host keeps its ranking (permanent redirects
   path-for-path, query and `#` fragment preserved, canonical/sitemap/og on
   the new host, Search Console change of address, old host redirecting for
   good).
3. **Cards are product, not brand.** Card anatomy, deck palettes,
   `bottom-orange`, diagram label rule, print output: untouched. The rebrand
   is the chrome around the card.
4. **Release safety.** Saved scales live in `localStorage` (`hpfc` and the
   saved-scale keys), which is per ORIGIN. A new domain starts empty. The plan
   must carry every user's saved scales across, or it is not a plan. Every
   older share link must still open on the new host.
5. All `CLAUDE.md` hard constraints hold (single file, generated regions,
   "scale" never "deck" in visible text, dev-first lanes, i18n step).

## How to work (optimise for iteration speed)

1. **Ask only what is still open, briefly.** The four decisions above are
   settled. If something else blocks you, ask at most three questions, each
   with your recommended default, and proceed on the defaults if there is no
   answer.
2. **Diverge.** Produce 3 to 5 genuinely different directions for the app
   chrome, not variations of one. Vary real axes: wordmark face (Marcellus,
   which is already loaded, vs the board's Playfair/Cormorant suggestion);
   header layout (mock: link button, horizontal lockup, menu button; or
   alternatives); how the chords-and-progressions subtitle reads at the
   root; how much of the teal/gold glow appears outside the mark;
   ground (the board's `#0F0E0B` vs today's warm `#1a1815` gradient); how the
   tagline and the scale chips sit. These axes are examples: invent others
   if the brand suggests them, and treat the mock as one direction, not the
   answer. Moving or restyling a control is fine; changing what it does is
   not. One direction may be the conservative "swap the header, change
   nothing else"; at least one should be bolder than the mock.
3. **Make each direction cheap and visible.** A throwaway static HTML mock
   per direction (copy of the header and one card, real tokens, no app JS),
   screenshotted with the preinstalled Playwright at 380 px and 1280 px wide,
   or published as private artifacts. Do not touch `index.html`, run the full
   test suite, or open PRs during exploration. Timebox each direction; a
   rough mock that shows the idea beats a polished one. Build directions in
   parallel (one subagent each, same inputs, told to differ from the
   others), and research the domain-move questions in another while they
   run.
4. **Compare, then converge.** One table: direction, what it changes,
   effort, risk to tests (which pinned strings move), reversibility, and
   your pick with a reason. Stop and let the owner choose before writing
   lane-level detail for one direction.
5. **Separate the reversible from the irreversible.** Visual chrome is
   cheap to change and change back. The domain move (DNS, `CNAME`, canonical,
   redirects, Search Console, GA stream) and the storage hand-off are not;
   sequence them last, each behind an explicit owner go.

## The plan document

Write it to `docs/plans/2026-10-31-handpan-theory-rebrand.md` (docs-only, so
CI skips it). Keep it short; link instead of restating `CLAUDE.md`. It holds:

- **Options and the pick:** the comparison table and the owner's choice (or
  "pending").
- **Open decisions:** each with options, a default, and whether it can be
  reversed later.
- **Phases**, each shippable alone, dev-first per `CLAUDE.md`:
  1. Brand chrome on the current host (header, icon set via
     `tools/make_icons.py`, `og.png`, theme-color, i18n keys) with no host
     change.
  2. Dual-host readiness: the new host serves the same bytes, canonical still
     points at the old host, and the saved-scale hand-off is built and tested.
  3. Cutover: canonical/og/sitemap/llms/JSON-LD/scale pages to the new host,
     old host 301s path-for-path, Search Console change of address.
  4. Clean-up after it holds: tests and docs that still name the old host.
  For each phase: files touched, which pinned tests change and why, how to
  verify on DEV, and how to roll back.
- **Storage hand-off options** (at least two, e.g. a one-time redirect that
  carries saved records in the fragment, or an export/import prompt on the
  old host), with the failure modes of each (private browsing, very large
  stores, users who never revisit the old host). Note the tension with a
  blanket Cloudflare 301 on the old host: once every request redirects at
  the edge, the old origin's script never runs and its saved scales can no
  longer be read. Say how the plan resolves that (for example, the old host
  keeps serving a hand-off page for a while, or the redirect lets the app
  load first).
- **Kill criteria:** what would make you stop or back out (ranking drop
  threshold, lost-scale reports, redirect loops).
